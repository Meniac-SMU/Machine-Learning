## 범위와 결론

사용자 요청은 프로젝트 구조·코드·기존 학습 증거 확인과 수정안 제시다. 이번 작업에서는 런타임, 보상 값, YAML, 모델, 빌드를 변경하거나 신규 경기·학습을 실행하지 않았다. 현재 활성 경로인 `Assets/_Soccer/Manager`를 중심으로 관측 → 마스크 → PPO 명령 → Planner → Executor → 물리/사건 → 보상 → trainer → 평가/승격을 검토했다. 과거 선수 학습 Core 경로와 현재 MNG 경로를 혼동하지 않는다.

결론: 실제 PPO 학습은 이루어졌지만, 현재 시스템은 '과거 모델을 지속적으로 이기는 모델'을 고르고 유지하도록 설계되어 있지 않다. 300k가 부족할 가능성과 별개로 **승격 기준의 목표 불일치, 전략을 대신하는 Planner, 관측되지 않는 실행 상태, 제한된 상대 풀과 탐색 감소, 보상에 종속된 전술 지표**를 먼저 다뤄야 한다. 수백만 step만 추가하면 과거 정책을 압도한다는 보장은 없다.

검증한 Runtime C# 52개와 MS3 YAML, 총 53개 파일은 MS3 최종 source snapshot의 SHA와 일치했다. 기존 대전 JSON과 TensorBoard를 다시 계산한 결과는 `Logs/MNG-MS/architecture-audit-20260922/existing-evidence-analysis.json`에 저장했다. 재계산 스크립트도 같은 폴더에 보존했다.

## 1. 기존 결과가 실제로 보여 주는 것

점수율은 `(승 + 0.5 × 무) / 경기 수`이며 순수 승률과 다르다.

| 300k 정책의 상대 | 300k 점수율 | 평가량 | 판단 |
|---|---:|---:|---|
| R0-Full | 87.5% | 정책 40경기, 별도 무작위 40경기 | 이 고정 상대에 강함 |
| 초기 P0 | 55.0% | 양 진영 총 40경기 | 표본상 근소 우세, 압도 아님 |
| 100k | 40.0% | 양 진영 총 40경기 | 표본상 열세 |
| 200k | 38.75% | 양 진영 총 40경기 | 표본상 열세 |

- R0-Full의 무작위 유효명령 감독 점수율은 16.25%. 같은 하위 코드를 쓰는 정책 사이 격차는 신경망 선택이 결과에 기여한다는 증거다. 다만 무작위보다 강하다는 것만으로 복잡한 장기 전술 습득까지 증명하지는 못한다.
- 세 과거 정책 상대 합산은 45승 17무 58패, 점수율 44.58%다. 기존 완료는 MS3 파이프라인/R0 gate 완료이며, 사용자 목표인 역사 정책 전체에 대한 우위는 미달이다.
- 100k/200k R0 검사는 120초·정책 20경기, 300k는 300초·정책 40경기였다. `72.5 → 62.5 → 87.5%`를 동일 조건의 학습 곡선으로 해석하면 안 된다. 분당 정규화도 경기 길이에 따른 승패 분포·후반 전술 차이를 없애지 못한다.
- 같은 seed 순번의 양 진영을 묶어 20개 그룹을 20,000회 재표집한 기술적 95% bootstrap 구간: 초기 상대 43.75~65%, 100k 상대 27.5~53.75%, 200k 상대 28.75~48.75%. 고정 seed 가족·사후 모델 선택·다중 비교 한계가 있어 일반화된 유의성 검정으로 쓰지 않는다. 특히 초기 상대 55%를 확정적 발전으로 과장하지 않는다.
- 100k 대 200k 대전과 새로운 seed 가족의 전체 리그는 없다. 지금 100k 또는 200k를 새 챔피언으로 확정할 수 없다.

## 2. 우선 수정할 구조 문제

### A. 승격 기준이 사용자 목표를 검사하지 않음 — 확정

`Tools/MNG_MS3_Assess.ps1:102`의 완료 판정은 R0 점수율, P0 대비 R0 회귀, 전술 지표 1개 5% 개선에 집중한다. `MNG_MS3_Protocol_v1.json`에도 checkpoint 리그 승격 조건이 없다. 그래서 과거 정책에 져도 MS3 완료가 가능했다.

수정안: '최신 checkpoint'와 '사용할 champion'을 분리한다. 최신 모델은 연구 후보, champion은 고정 리그를 통과한 모델로 유지한다. R0는 보조 회귀 시험으로 유지하고 과거 champion·초기·중간·다른 스타일 정책을 주요 평가 상대로 삼는다. 훈련 보상이나 자체 ELO만으로 교체하지 않는다.

### B. 전략 선택을 하위 코드가 대신하는 구간 — 확정, 성능 기여량은 미측정

`MNG_ManagerAgent.OnActionReceived`에서 P0의 `None`은 raw command를 그대로 전달한다. 이것은 정상이다. 그러나 명령 전달 뒤의 동작이 모두 신경망의 선택에 의해 달라진다는 뜻은 아니다.

하위 이동·회전·공 접근·킥 접촉·충돌 방지는 현재 프로젝트의 유효한 기술 계층이다. 모두 제거하면 선수별 학습의 원래 병목으로 돌아간다. **물리 실행은 유지하고, 압박·지원·패스/슛 의도 같은 전략 선택을 PPO 명령에 연결하는 P1이 우선**이다. P1은 아직 미적용이며 이번 감사도 제안만 수행했다.

공통 Planner 변경은 RL과 규칙형 양쪽에 대칭 적용해야 한다. 그러면 변경 후 R0도 같은 이름의 이전 R0와 동일 환경이 아니므로 별도 버전·빌드·평가로 구분한다. 과거 모델과의 비교도 동일한 새 실행 코드에서 수행해야 한다.

### C. 실제 임무 거절과 실행 상태가 신경망에 보이지 않음 — 확정

`MNG_PlayerSkillExecutor.cs:377`의 `SetTask`는 기존 킥이 끝나지 않거나 수신 임무가 유지 중이면 새 임무를 거절한다. 킥 임무는 2초, 골키퍼 배급은 3초까지 유효하다. 감독 판단은 0.5초 주기이므로 여러 판단 동안 이전 행동이 지속될 수 있다. `MNG_MatchController.cs:536`는 `SetTask`의 반환값을 기록하지 않는다.

`MNG_ObservationWriter.cs`의 133개 값에는 현재 임무 종류/잔여 시간/킥 실행 중 여부/정체 개입 상태가 없다. `PreviousCommand`는 최근 수락된 감독 명령이지 실제 실행 중 임무가 아니다. 현재 모델에는 memory도 없다.

이 동작은 안전한 킥 완료를 위한 의도적 지속 실행일 수 있으며, raw/effective 로그가 거짓이거나 P0 명령 교체가 재발했다는 뜻은 아니다. 하지만 PPO가 '지금 선택한 명령이 언제 적용되는지' 알기 어려운 부분 관측 문제다.

수정안: requested command → planned tasks → accepted/rejected tasks → executed skill/physical event까지 구분하는 추적 추가. 실행 임무 종류·잔여 잠금·정체 활성 여부를 관측 v2에 추가하고 명령 교체 가능/불가 계약을 명확히 한다. 우선은 관측 추가가 RNN 도입보다 단순하다. 관측 차원 변경 시 기존 PT 직접 호환을 주장하지 말고 새 schema·새 Run으로 학습하거나 검증된 입력 확장 이식 절차를 사용한다.

### D. 전술 지표가 보상 cap에 종속됨 — 확정된 계측 결함

`MNG_TacticalRewardTracker.cs:122,176,200`은 `Award(...) != 0`일 때만 유효 슛·완료 패스·5m 전진 카운터를 증가시킨다. `MNG_EventLedger`는 종류별 cap과 분당 절대 shaping cap을 적용한다. 동일한 실제 플레이도 다른 보상 사건이 먼저 cap을 소비하면 관측된 전술 지표가 달라진다.

따라서 이전 완료 보고서의 유효 슛 `1.72 → 1.825/분`, +6.1%는 **보상 지급된 유효 슛 카운터 증가**다. 실측 슛 전체 증가나 전술 발전의 독립 증거로 쓰기 어렵다. 골·승패 결과에는 이 카운터 문제가 적용되지 않는다.

`IsGoalOpeningTrajectory`도 실제 이후 궤적이나 수비수 차단을 측정하는 것이 아니라 실제 킥 발생 시점의 `origin → target` 직선이 골문 범위를 향하는지 검사한다. 지표명을 그 정의에 맞게 명확히 하고 실제 골문 통과/차단/세이브와 분리한다.

패스는 `pending.ReceiverSlot=-1`에서 시작해 실제 다른 동료를 수신자로 잡는다. '처음 의도한 수신자에게 도달했는가'는 저장하지 않는다. 실제 동료 수신과 의도 수신 성공은 서로 다른 지표로 추가한다. 한편 킥 직후 소유권은 BallControl에서 먼저 해제하므로, 코드만 보고 '패스 직후 기존 소유 때문에 모두 취소된다'고 단정하지 않는다.

수정안: raw event count, rewarded event count, reward amount, cap-suppressed count를 분리. 진척 판정은 raw 사건과 경기 결과로 수행. 명령별 슛/패스와 safety/keeper 자동 사건의 출처도 기록한다. 보상 자체를 바꾸지 않는 계측 수정부터 가능하다.

## 3. 학습량과 self-play 설정

### 300k의 실제 규모

- 32환경 합산 학습팀 decision transition 300,028개이며, 32배를 다시 곱하지 않는다. installed `ghost/trainer.py`는 한 팀의 trajectory만 PPO에 보내고 반대편은 고정 opponent로 처리한다. Red와 Navy가 매 순간 각각 독립 optimizer로 동시에 학습하는 형태가 아니다.
- 0.5초 주기의 300초 경기에서 대략 600 decision. 300k는 대략 500경기 분량, 실제 완료 기록은 484경기다. 초기 가중치는 MS2 P0이므로 완전 무학습 상태에서 484경기만 한 모델도 아니다.
- buffer 4096 기준 대략 73개 경험 버퍼 분량이며 각 버퍼에 3 epoch를 수행한다. 73번의 단일 gradient update라는 뜻은 아니다.
- 상대 snapshot 교체 11회, 학습 팀 교대는 101,512/201,604에서 총 2회. 스스로 새로운 상대들에 여러 번 적응하는 실험으로는 짧다.
- 3M은 대략 5,000경기 분량이므로 발전할 여지는 있다. 충분성의 보장은 아니며, 구조 문제나 좁은 상대 풀은 데이터 증가만으로 사라지지 않는다.

### 상대 풀과 학습률

현재 YAML은 save/swap 25k, team change 100k, window 10, latest ratio 0.5다. 설치된 GhostTrainer는 과거 snapshot을 순환 배열에 덮어쓴다. 따라서 학습을 수백만으로 늘려도 모든 과거 강자에게 연습하는 구조가 아니다. 최신 10개 중심이며 '나를 이겼던 과거 champion'을 보존한다는 계약이 없다. 또한 같은 팀 policy queue로 상대 가중치를 배포하므로 32환경이 자동으로 서로 다른 32종 정책을 상대한다는 의미도 아니다.

기록상 학습률은 초반 0.00004885에서 297k의 약 0.000000635로 감소했다. entropy는 약 0.94에서 0.66으로 감소했다. beta와 epsilon도 resolved configuration에서는 linear다. 300k 종료 부근까지 탐색·갱신 폭이 줄어드는 설정이다. entropy 감소 자체는 정상 학습에서도 발생하므로 이것만으로 붕괴라고 부르지 않는다.

ELO는 마지막 약 1190.49이며 초기 1200보다 높지 않다. 변화하는 내부 상대 풀의 ELO는 고정 외부 실력 기준이 아니므로 이 숫자만으로 퇴보를 확정하지 않는다. 누적 보상도 단조 상승이 아니었다.

수정안: 동일 환경으로 진단 Run을 만들 때 총 예산과 schedule을 함께 고정한다. 기존 300k optimizer/schedule을 그대로 둔 채 단순 resume만 하는 방식은 피한다. `max_steps`를 늘리면 linear schedule 자체가 재계산되므로 그것 역시 동일 설정의 단순 연장이라고 기록하면 안 된다. 새 Run과 초기 가중치/optimizer/seed/schedule을 명시한다.

빠른 후보 설정은 **제안값**으로 save 25k 유지, swap 10k, team change 50k, window 30, latest ratio 0.3, learning rate 5e-5 constant 및 beta 0.003 constant다. 이 값을 전부 한 번에 '최적값'으로 적용하지 않는다. 먼저 상대 구성 변경과 탐색 schedule 변경을 별도 실험으로 비교한다. 30개 window도 3M 전체 역사 보존을 해결하지 못하므로 장기 단계에는 역사 champion 고정 풀을 별도로 유지하는 기능이 필요하다. 매 worker 서로 다른 상대 또는 혼합 R0/PPO 상대는 YAML 한 줄 변경으로 구현된다고 가정하지 않는다.

### 보상 목적

현재 골 +1/-1, 승패 +0.5/-0.5, 유효 슛 +0.02, 완료 패스 +0.06, 전진 +0.01, 회수 +0.03, 빠른 회수 +0.02이며 shaping 절대 합 cap은 분당 0.25다. 사건 중심과 cap은 악용 방지에 유효하다. 이 값이 학습 실패를 일으켰다고 확정할 증거는 없다.

다만 중간 shaping은 양 팀에 각각 양의 보상을 줄 수 있어 완전 zero-sum이 아니며, 득실차 최적화와 '최종 승리 확률 최대화'는 같은 목적이 아니다. 현재 `gamma=.995`에서는 약 600 판단 뒤의 terminal 보상이 초반에 약 4.94% 가중치로 할인된다. time_horizon 128은 약 64초이고 그 너머도 value bootstrap으로 학습하므로 '64초 이후를 전혀 배우지 못한다'는 해석은 틀리다. 장기 승리보다 당장의 전진/회수에 치우칠 수 있는지는 행동 증거와 함께 검사해야 한다.

`AwardSelfPlayTerminalResult`의 마지막 `SetReward(±0.5/0)`는 installed GhostTrainer가 마지막 reward 부호로 승패/ELO를 판정하는 계약을 맞춘 것이다. 무조건 AddReward로 바꾸면 마지막 shaping에 의해 무승부를 승리로 오인할 수 있다. 마지막 decision 구간의 reward를 덮어쓰며 ledger cumulative와 trainer reward가 다를 수 있으므로 별도 정합성 계측을 권장한다. 이는 episode 전체의 과거 보상을 지운다는 뜻이 아니다.

## 4. 규칙형 상대가 문제인가

MS1의 Easy는 속도 0.35배/판단 1.5초, Full은 속도 1배/판단 0.5초다. `MNG_MSOpponentProfile`에서 난이도는 주로 신체 속도와 판단 주기이며 다양한 전술 지능의 단계가 아니다. R0는 고정 조건문, 1초 최소 명령 유지, 슛 기회 우선, 패스 수신자 점수 계산을 사용한다.

R0는 충분히 유용한 초기 학습 상대였지만, Full이라는 이름만으로 강한 모든 전술의 대표가 되지는 않는다. 특히 R0의 패스/슛 우선순위를 공략하는 정책이 좋은 R0 점수만 낼 수 있다. 현재 MS3는 PPO 상대 학습이므로 '약한 R0만 계속 학습해서 실패'라는 설명은 부정확하다. 초기 편향과 R0 중심 모델 선택에는 영향을 줄 수 있다.

전술적으로 더 나은 R0 한 종류만 추가하는 것보다 압박형·후방수비형·패스형의 서로 다른 상대와 과거 PPO 강자를 섞는 것이 일반 대응력 평가에 적합하다. 선수 속도를 높여서 강하게 만드는 것은 감독 지능과 물리 능력을 혼합하므로 별도 스트레스 시험으로 취급한다.

## 6. 권장 개발·실험 순서

### 1) 평가를 먼저 맞춤

- 보상 지급 여부와 독립적인 사건 계측 및 실행 임무 수락/거절 telemetry 추가.
- 초기·100k·200k·300k 전 조합을 동일 300초·같은 진영/seed 프로토콜로 비교. R0도 동일 경기 길이로 다시 비교.
- 개발용 seed와 승격용 holdout seed 분리. 경계 사례만 경기 수 확대. 모델/코드/프로토콜 SHA 보존.
- '항상 회수', '항상 균형', '소유하면 전진·슛 가능하면 슛'의 단순 baseline과 비교. 고정 명령이 mask되면 사용하는 fallback 규칙을 명시. 무작위만 이기는 모델과 상태를 읽어 단순 규칙도 이기는 모델을 구별.
- 진단용 대표 상태에서 여섯 명령을 각각 Planner에 넣어 task 종류/인원/목표 위치 차이를 비교. 이후 동일 snapshot 단기 rollout으로 실제 결과 차이 확인. 동일 상태 비교 없이 서로 다른 경기 action 비중을 인과 증거로 해석하지 않음.

### 2) 전략 개입을 분리하는 P1을 작은 단위로 적용

- 먼저 압박/후방 보호 인원 차이, 다음 공격 지원, 다음 keeper/stall 전술 개입을 순차 적용.
- 킥 잠금/정체 상태를 관측 v2로 노출. 매 변경 뒤 실행 안정성과 명령 간 차이를 검증.
- 물리 안정화는 유지. 중립 reset으로 정체를 해소할 경우 이를 이용한 위험 회피 exploit이 생기지 않도록 조건·출처·보상 영향을 검증.
- 새 환경에서는 같은 실행 코드로 과거 정책도 재평가. 관측 schema가 달라지면 이전 모델 입력을 기존 133개로 투영하는 검증된 adapter 또는 별도 호환 endpoint가 필요. 단순히 새 관측을 예전 ONNX에 입력하지 않음.

### 3) 원인 분리를 위한 제한된 학습

- 학습량 자체의 효과를 먼저 정량화하려면 현행 환경/보상/상대 설정을 고정한 control Run에서 총 1M 예산을 처음부터 선언하고 같은 초기 P0·새 optimizer로 수행. 100k/300k/1M 동일 리그 평가. linear 1M과 과거 linear 300k는 schedule이 다르므로 순수 step 차이만의 실험이라고 주장하지 않음.
- 실용적 개선이 우선이면 위 진단 후 P1 환경에서 새 학습 시작. 첫 300k로 명령 효과와 실제 사건 개선 확인, 이어 1M까지 100k 단위 검사. 진전이 지속될 때만 2M, 최대 3M의 별도 예산 승인/설정으로 확장.
- 관측 변경 후 무학습 시작이 필요한 경우 적합한 짧은 상황학습을 먼저 재사용하고, 이전 모델과 직접적인 step 수 비교 대신 동일 새 환경의 control과 비교.
- 최소 2개 학습 seed로 주요 결과 재현. 32환경 유지. 50k 모니터링/100k 상세 리그/초기·완료 inspector 저장 유지.
- 불리한 과거 champion을 opponent 풀에 보존. 단계 초반에는 stock window를 확대해 시작할 수 있지만 장기 목표에는 영구 보존 풀 기능이 필요.
- reward schedule 조정은 별도 비교군. P1·보상·관측·네트워크 크기·상대 전부를 동시에 바꾼 뒤 특정 원인의 효과라고 주장하지 않음.

### 4) champion 승격 규칙의 제안

다음 수치는 새 실험 설계 제안이며 기존 결과를 소급 합격시키는 기준이 아니다.

- 직전 champion 상대 점수율 0.60 이상이며, 사전 정한 holdout 재표집 구간 하한이 0.50 초과.
- 고정 역사 풀 평균 0.55 이상, 중요 개별 상대 0.45 미만이면 승격 보류/약점 학습. 리그 가중치는 사전 동결.
- R0-Full은 현행 champion 대비 점수율 0.05 초과 하락 시 회귀 조사. 동일 길이/충분한 표본에서 비교.
- 진영별 결과·득실·명령-임무 추적·보상 악용 확인. 개선 없는 2개 연속 상세 평가에서는 예산 자동 소진 대신 원인 검토.
- '과거 모델 압도'는 더 높은 별도 목표(예: 역사 주요 상대마다 0.70 이상)로 명시. 평균 우세와 전 상대 압도를 구별.
- checkpoint마다 단조 우월을 요구하지 않는다. 학습 중 후보는 나빠질 수 있지만, 승격 실패 시 기존 champion을 유지하여 실제 제공 모델이 퇴보하지 않게 함.

## 7. 해석의 한계와 외부 근거

현재 증거는 설계상 원인 후보를 찾기에 충분하지만 각 원인이 승률을 몇 % 바꾸는지는 P1/상대/보상 통제 실험 전에는 알 수 없다. 이번에는 신규 경기나 학습을 하지 않았다. 네트워크 128×2의 용량 부족, 패스 기술 성공률 부족, R0 상대 과적응도 독립 실험 없이 확정하지 않는다.

Unity 공식 문서는 self-play에서 상대 다양성/안정성의 trade-off, 과거 snapshot window, team/swap 주기, 보수적인 shaping을 설명한다. AlphaStar 논문은 정책 간 상성과 다양한 과거 상대에 대응하는 league 훈련을 설명한다. 이는 프로젝트 수정안의 일반적 근거이며 현재 프로젝트의 특정 원인이 증명됐다는 뜻은 아니다.

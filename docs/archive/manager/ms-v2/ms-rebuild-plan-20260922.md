## 1. 목표와 우선순위

목표는 같은 기술 실행 조건에서 감독의 판단 차이가 선수 배치·압박·공격 의도에 반영되고, 학습 후속 모델이 과거 모델보다 강하다는 사실을 독립 경기로 입증하는 것이다. 학습 중 모든 checkpoint의 단조 개선을 보장하지 않으며, 검증을 통과한 champion만 교체하여 제공 모델의 퇴보를 막는다.

이 계획과 연결된 [런타임 구현 계약](ms-rebuild-runtime-contract-20260922.md), [학습·평가 계약](ms-rebuild-training-validation-20260922.md)이 이전 MS3의 133관측 유지, 300k 조기 완료, 50k 점검/100k 평가, 기존 MS3 모델 선택 지시보다 우선한다. 기존 완료 보고서는 당시 사실로 보존한다. [2026-09-22 감사](rl-architecture-audit-20260922.md)는 원인과 근거 자료이며 새로운 예산·일정은 이 계획을 따른다.

| 사용자 제안 | 채택 내용 및 필요한 보완 |
|---|---|
| 기존 300k MS3 모델 폐기 | 기존 MS3 계열 전체를 향후 초기값·승격 후보·시연 기본값에서 제외. 파일 삭제가 아닌 선택 자격 철회. 이전 100k/200k로 대체하지 않음 |
| 보류했던 P1 완성 | 공통 기술 실행 유지, 감독 명령별 압박 인원·지원·후방 배치·킥 의도 분리 |
| 이전 킥/수신 때문에 새 명령 무시되는 문제 해결 | 취소 가능한 준비 동작과 짧은 물리 commitment 분리, 실행 관측·거절 이유·사건 추적 추가 |
| 전술 평가 정비 | raw 사건과 reward 지급 사건 분리, 의도 패스와 실제 수신 구분, 자동 안전 동작 출처 기록 |
| self-play 32환경, 100k/200k | 그대로 채택. 100k 모니터링, 200k 상세 평가. 저장 주기는 별도 100k 이하로 운용 |
| 최소 400k, 좋은 추이로 1M | 정상 self-play 한 실험의 최소 400k. 오류/악용 중단 예외. 400k부터 200k 단위 연장, 1M에서 엄격 검증 |
| 수백만까지 개선 | 1M 검증 뒤 같은 버전이면 200k 단위 최대 2M, 다음 엄격 검증 뒤 3M. 무제한 연장 금지 |
| 필요하면 MS2까지 복귀 | **새 관측 v2로 fresh PPO → 짧은 MS2-v2 준비 → MS3-v2**를 기본안으로 선정. 과거 선수별 학습부터 반복하지 않음 |

## 2. 폐기와 보존의 정확한 의미

- 폐기 대상: `MNG_MS3-20260921-r001/r002`와 그 초기~300k MS3 checkpoint의 현행 모델 자격. 재학습 초기값, 자동 resume, 챔피언, 기본 리뷰 빌드로 사용하지 않는다.
- P0 이전 MS2 모델도 새 관측 v2에 직접 연결하지 않는다. 기존 MS3의 부모 정책이라는 이유로 초기값을 자동 재사용하지 않는다.
- 기존 PT·ONNX·logs·source snapshots·씬·빌드·보고서는 이력으로 보존한다. 이번 계획 단계에서 파일 이동/삭제/모델 reference 수정 없음.
- 구현 첫 단계에서 모델 registry/manifest에 `retired-architecture-v1`, 사유, 날짜, SHA를 기록하고 새 Builder/실행기에서 해당 후보의 기본 선택을 거부한다. 기존 빌드는 '구조 개편 전 기록용'으로 안내한다.
- 과거 모델과 새 schema adapter를 만드는 작업은 첫 실험의 필수가 아니다. 새 환경에서 생성된 초기/200k/400k 정책이 기본 역사 비교 대상이다. 구 MS3 수치와 신 모델 수치를 다른 환경 상태 그대로 직접 비교하지 않는다.

## 3. 진행 단계와 산출물

| 순서 | 작업 | 산출물 | 다음 단계 조건 |
|---|---|---|---|
| R1 | 현재 작업 트리 보존·v2 계약 동결 | source SHA, 은퇴 registry, schema/버전 명세 | 기존 Run 및 사용자 변경 보존 |
| R2 | 사건 계측·task 수명·실행 관측 | command/task/kick/event 연결, 새 observation writer | 사건 중복 0, task 거절 이유 누락 0 |
| R3 | P1 전략 의미 분리 | 명령별 Planner, 안전 동작 경계 | fixture와 짧은 rollout에서 의도한 차이 확인 |
| R4 | Unity 검증·훈련/평가 Player 빌드 | compile/Builder/tests, build SHA, 32환경 smoke/resume 증거 | 오류·NaN·schema mismatch 없음 |
| R5 | fresh MS2-v2 준비 학습 | v2 초기 정책, 0-step baseline, 고정 평가 | 아래 준비 gate 통과 |
| R6 | MS3-v2 self-play 최소 400k | 100k 점검·200k 리그·PT/ONNX | 승격 가능성 및 안정성 판정 |
| R7 | 개선 시 600k/800k/1M | champion 이력, 1M 엄격 평가 | 이전 정책 우위와 독립 재현 |
| R8 | 한 가설씩 수정 후 2M/3M | 비교 실험, 버전별 리그 | 각 확장 상한의 엄격 평가 통과 |

R2/R3를 큰 변경 하나로 합치지 않는다. 계측/임무 계약 → 압박/수비 → 공격 지원 → keeper/stall 순으로 구현하고 관련 검증을 각각 수행한다. 물리 파라미터와 보상 숫자, 상대 지능까지 한 번에 바꾸지 않는다.

## 4. MS2-v2 준비 학습

- 관측 schema 변경으로 **새 신경망·새 optimizer**를 사용한다. 기존 step7443/99968/300028 초기값 없음. 기본 128×2 PPO 구조를 유지해 신경망 크기 변경을 원인에 섞지 않는다.
- self-play 진입용 준비만 수행하며 최소 400k self-play 예산과 별도로 기록한다. 준비 상한 200k, 32환경, 점검 100k·평가 200k. crash/무결성은 상시 검사한다.
- 100k 시점에 득점/킥 신호가 전혀 없으면 200k를 무조건 소비하지 않고 task·mask·기술 도달 가능성 진단. 저수준 기술 실패를 reward 증액으로 숨기지 않는다.
- 상대는 P1 공통 실행기를 쓰는 `R0-Full-v2`가 기본. 0~40k 동안 전혀 경기 신호가 나오지 않는 경우에만 별도 manifest에 기록하고 Medium을 최대 40k의 구조 구간으로 사용한 뒤 Full로 복귀한다. 쉬운 상대 결과를 Full 결과로 표시하지 않는다.
- 진입 gate 권장값: Full 40경기 점수율 0.40 이상, 무작위 유효명령 대비 +0.10 이상, 양 진영에서 의도 슛/회수 사건 발생, 장기 정체·무효 명령 반복·행동 무결성 실패 없음. 이는 self-play 연결을 위한 준비 gate이며 강한 감독 완료 판정이 아니다.
- 200k에서 미달이면 준비 stage를 실패로 기록하고 구조 원인을 조사한다. 자동으로 구 모델을 가져오거나 긴 MS1 커리큘럼을 부활시키지 않는다. 필요한 상황 fixture만 별도 보완 계획으로 사용한다.
- 통과 정책을 `self-play initial, step=0`으로 동결한다. 초기에는 champion이 아니라 reference 정책이다. MS3 첫 승격은 최소 400k 이후에만 가능하다.

## 6. 예상 위험과 대응

- P1 제거 후 초기 실력 하락: 기존 코드가 대신하던 판단을 실제 학습 문제로 돌려놓은 결과일 수 있다. 구 버전 승률을 즉시 복구하기 위해 자동 전술을 다시 넣지 않는다.
- 자동 동작 완전 제거로 정체: 기술 실행·충돌 방지는 유지한다. 명령과 무관한 '좋은 전술'을 주는 구조를 제거하는 것이 목적이다.
- 명령 변경마다 킥 취소: 물리 commitment만 짧게 보호하고 준비 동작은 교체 가능하게 한다. latency와 취소율을 함께 확인한다.
- 과거 정책과 가위바위보 상성: champion 단일 대전과 역사 풀 평균/최악 상대를 함께 평가. 모든 checkpoint를 이긴다는 보장 대신 검증된 개선과 알려진 약점을 표시한다.
- 수백만 경험 소진: 실제 승률/득실/조건부 전술과 신뢰 구간으로 연장을 결정. 훈련 reward 증가만으로 연장하지 않는다.
- 강화된 R0 제작이 일정 확대: 첫 재학습에서는 기존 R0의 판단 규칙을 유지하고 P1 실행기 적응만 한다. 전술형 R0 추가는 1M 이후 별도 단일 가설 실험으로 분리한다.

## 7. 에이전트 실행 지침과 중단·재개

1. 후속 구현 요청을 받으면 루트 AGENTS → 이 계획 → 런타임/학습 계약 → 현재 상태를 읽고 시작한다. 이번 문서 작성만으로 실행을 시작하지 않는다.
2. 실제 dirty 작업 트리를 snapshot하고 관련 파일 SHA를 기록한다. git HEAD만으로 보존했다고 판단하지 않는다. 자동 commit/push, `--force`, 기존 Run 덮어쓰기 금지.
3. 새 관측/임무 enum/보상 판정 변경은 문서·Builder·프로필·테스트를 함께 수정한다. 보상 변경 시 기존/변경/차이 표와 `docs/soccer/rewards.md` 동기화.
4. Unity compile → 관련 EditMode/PlayMode → Builder validate → Windows Player → 32 worker 및 resume smoke 순서로 검증. smoke용 모델은 정식 후보에 포함하지 않는다.
5. 최초 실행, 100k/200k, 단계 전환, 종료에 inspector·trainer log·worker 사건·PT/ONNX·SHA·상대 풀 상태를 보존한다. 입력 schema/실행기/물리 버전이 바뀌면 새 Run.
6. 사용량 비율에 따른 실행 제한은 폐지했다(2026-09-23). 오류·중단 시 증거와 재개점을 보존한다.
7. 재개 기록에는 Run/optimizer checkpoint/step/schema/build SHA/상대 풀 RNG/진영·swap counter/다음 평가점/champion·예산을 포함한다. self-play 상대 상태까지 복원되는지 검사하고, 복원 불가면 동일 연속 학습이라고 주장하지 않는다.
8. 학습 멈춤과 모델 은퇴를 구별한다. 정상 중단은 동일 optimizer로 resume, 구조 변경은 새 Run. 목표 step을 채우기 위한 실패 반복 금지.

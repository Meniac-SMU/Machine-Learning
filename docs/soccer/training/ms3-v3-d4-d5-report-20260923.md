## 현재 결정과 완료 범위

2026-09-23 사용자 지시에 따라 현행 단계 명칭을 v3로 구분한다. **MS2-v3는 사용자가 직접 확인한 최신 경기 규칙과 기존 승인 MS2 가중치를 결합한 출발 기준**이다. MS2를 이번에 다시 학습했다는 뜻이 아니다. MS3-v3는 이 MS2 actor에서 step 0, 새 optimizer, 새 상대 풀로 시작한다. 이번 작업은 D5 준비 완료까지이며 학습 step·optimizer update·모델 승격은 모두 0이다.

기존 MS3-v2 r005의 400k는 초기값·상대 풀·평가 기준·champion·기본 시연에서 제외한다. PT/ONNX/log/빌드와 과거 registry는 삭제하지 않는다. 현행 registry는 `ms-v3-model-registry.json`, 현행 계약은 `ms-v3-schema.json`이며 champion은 아직 없다. 내부 Behavior `MNG_ManagerV2`, 관측244/행동6, MS3V2 빌드·YAML 이름은 호환 ABI이므로 유지한다. 단계/Run 세대 v3와 기술 스키마 v2는 서로 다른 구분이다.

## 변경 사항

- 새 registry/schema와 정책 계보 검사기로 MS2만 초기 actor로 허용한다. v3 평가 입력은 MS2, 새 v3 Run 후보, 규칙형·무작위 baseline만 허용한다. 제외한 400k의 hash와 외부 history 사용을 차단한다.
- 준비 도구는 actor-only 사본의 global_step만0으로 바꾸며 원본 Policy와 원본 step200120을 보존한다. optimizer를 가져오지 않는다. 준비 receipt·32환경 검사·실행 소스·빌드·정책을 SHA로 연결한다.
- 학습 실행기에 v3 명명·현행 runtime 검사와 `-ValidateOnly`를 추가했다. 검증 모드는 Run 디렉터리나 trainer를 생성하지 않는다. 새 v3 manifest에는 MS2 원본 및 초기 snapshot 계보를 기록한다.
- 상대 풀은 초기 MS2 하나를 pinned로 사용하고 이후 이 새 Run에서 나온 snapshot만 누적한다. 기존 latest30%/recent50%/pinned20% 선택 비율과 PPO 설정은 바꾸지 않는다. v3 pool에는 세대/초기 snapshot hash를 기록하며 구 pool, 외부 history, 다른 초기 가중치, 추가 pinned는 거부한다.
- `Tools/mng_v3_evaluate.py`를 새 평가 진입점으로 추가했다. 양쪽 모두 최신 공통 규칙을 사용한다. `Tools/watch_mng_v3.py`는 MS2-v3끼리 1배속300초를 실행하는 진입점이다. 구 v2 도구는 과거 재현용이며 앞으로의 기본 진입점으로 쓰지 않는다.
- 게임 C#·씬·모델 가중치·보상·마스크는 이번에 수정하지 않았다. 부족한 패스 빈도를 추가 강제 명령이나 quota로 해결하지 않는다.

## D4 기준선: 경기 결과와 해석

승점률은 `(승 + 0.5×무)/경기수`다. 모든 후보는 MS2 출발 정책이며 마지막 행만 무작위 유효명령 후보다.

| 후보 대 상대 | 경기수 | 승/무/패 | 승점률 | 득점:실점 |
|---|---:|---:|---:|---:|
| MS2 대 동일 MS2 | 40 | 15/6/19 | 45% | 128:132 |
| MS2 대 규칙형 Full | 8 | 5/1/2 | 68.75% | 40:33 |
| MS2 대 Recover 전용 | 8 | 4/1/3 | 56.25% | 22:20 |
| MS2 대 carry-shot | 8 | 1/2/5 | 25% | 25:28 |
| MS2 대 Balanced | 8 | 6/0/2 | 75% | 21:14 |
| 무작위 유효명령 대 Full | 8 | 0/0/8 | 0% | 7:83 |

동일 정책은10개 독립 seed(595001~)에 진영·정책 난수 스트림을 교차한40경기다. 나머지는 각각4seed×양 진영8경기이며595101/595111/595121/595131/595141부터 시작한다. 동일 정책이어도 샘플링과 비트 단위로 대칭이지 않은 물리 전개 때문에 지정 후보의 결과가 정확히50%가 되지는 않는다.

동일 정책의 지정 후보가 Red일 때35%, Navy일 때55%였다. 차이는-20%p, seed cluster95% 구간은 **[-55,+17.5]%p**다. 초기 위치·방향·관측 미러 검사를 통과했으며 결정적 진영 코드 결함을 나타내는 새 무결성 오류는 없었다. 그러나 넓은 구간에0이 들어간다는 사실은 진영 동등성의 증명이 아니다. D4 판정은 **원인 분리와 한정 학습 진입 가능**이며, 최종 공정성·성능 승격 승인으로 확대하지 않는다. 후속 평가에서도 진영별 지표를 유지하고 반복된 한쪽 열세가 나오면 학습 확장 전에 다시 진단한다.

Full 대비 무작위보다 나았지만 carry-shot 상대에 열세였고 패스 선택도 드물다. 이는 새 학습이 개선해야 할 기준선이다. 동일 정책40경기에서 지정 후보의 전체 패스 strike57회에는 걷어내기 등 여러 출처가 섞이므로 감독 PassBuild 개선 수치로 간주하지 않는다. 선택→취소/준비→실제 strike→수신을 구분한 trace를 후속 학습과 비교한다. 패스 최소 횟수를 새로운 합격 조건으로 만들지 않는다.

## 준비 패키지와 실행 경계

준비 폴더: `Logs/MNG-Rebuild/MS3-v3-D5-prepared-20260923`.

- `manifest.json`: readyToStart=true, trainingStarted=false, optimizerUpdates=0. 예약 Run `MNG_MS3V3-20260923-r001`; results/Run과 학습 evidence/Run은 생성하지 않았다.
- `initial-policy.pt`: 승인 MS2 actor 사본, step0, optimizer 없음.
- `preparation-gate.json`: 현행 runtime·초기 actor·receipt·preflight 연결.
- `config-preview.yaml`: 기존 PPO 설정,32환경, 최대200k.
- `launch-first-100k.ps1`: 첫100k에서 정상 저장 후 정지. 이번에는 `-ValidateOnly`만 실행했다.
- `resume-to-200k.ps1`: 같은 Run/runtime의100k 모니터링 통과 기록이 있어야 재개. 검증 스위치는 실제 실행기로 전달된다.
- `evaluate-checkpoint.ps1`: 명시한 checkpoint를 MS2/Full/Recover/carry-shot/Balanced와 각각20seed×양 진영40경기, 총200경기 평가한다. 학습이나 통과 receipt를 자동 생성하지 않는다. 비교 seed는596001/596101/596201/596301/596401로 고정한다.

명령은 저장소 루트 `C:/GitHub/Machine-Learning`에서 실행한다. 준비 이후 소스가 바뀌면 기존 준비물을 그대로 사용하지 말고 새 검증/준비를 만든다. 실제 시작은 다음 작업에서 수행한다.

```powershell
# 학습을 시작하지 않는 준비 검증
& ./Logs/MNG-Rebuild/MS3-v3-D5-prepared-20260923/launch-first-100k.ps1 -ValidateOnly

# 다음 학습 작업에서만 실행:100k까지 학습하고 저장/정지
& ./Logs/MNG-Rebuild/MS3-v3-D5-prepared-20260923/launch-first-100k.ps1

# 학습 후 실제 저장된 ONNX 경로를 명시
& ./Logs/MNG-Rebuild/MS3-v3-D5-prepared-20260923/evaluate-checkpoint.ps1 -Checkpoint 100000 -Candidate '<새 v3 Run의 ONNX 절대 경로>'
```

100k 점검은 crash/NaN·명령/보상 무결성, loss/KL/clip/entropy, 실제 learning-team 노출량, 저장된 pool/계보, 메모리/처리량, 상대별 성적·진영 격차, 패스 기회별 확률/취소/타격/수신, 정체·후방 위험·수비 개입을 함께 검토한다. 검토 기록을 `Logs/MNG-Rebuild/MNG_MS3V3-20260923-r001/monitor-100k.json`에 runId/runtimeSha/passed 및 근거 경로로 기록한 뒤에만200k 재개를 허용한다. 단순 reward 상승이나 파일 생성만으로 passed를 쓰지 않는다.

200k는 동일 평가를 반복하고100k 대비 진전/퇴행을 판단한다. 학습이 유효하면 별도 gate로400k까지 진행할 수 있지만 현재 실행 준비 상한은200k다.400k 정상 최소 목표가 있다고 해서 악화한 학습을 강제로 채우지 않는다. v3 이후 checkpoint는 같은 runtime에서 이력 후보로 평가하되, 예전 v2 400k를 되살리지 않는다. holdout seed996001부터40pairs는 이번에 사용하지 않고 최종 후보 검증용으로 보존한다.

R7의600k/800k/1M과 R8의2M/3M은 앞선 평가로 정당화될 때만 별도 준비한다. 이번 완료는 **대규모 학습에 진입하기 위한 D5 준비 완료**, 다음 실제 작업은 **MS3-v3 초기 자기대전(R6)의 첫100k**다.
